# JARVIS V10.1 — Ollama-Only Software Team Reliability Update

V9 is the local-AI final build of the JARVIS personal software-development operating system. It keeps the V1–V8 capabilities while removing cloud AI provider dependencies from the application code and routing all AI generation through a local Ollama server.

## V9 capabilities
- Local Ollama-only AI generation.
- No cloud AI API key is required by the JARVIS backend.
- Software developer team: planner, agents, dependencies, reviews, approvals and local Git checkpoints.
- Browser voice + Windows voice agent.
- Optional offline Vosk speech recognition.
- iPhone PWA/LAN remote console.
- Permission-based Windows desktop control and VS Code integration.
- Explicit approval-gated screen capture.
- Desktop emergency-stop and one-time desktop action claiming.
- Persistent memory and audit logs.
- Production configuration validation and security headers.
- Production startup and health-check scripts.

## Ollama setup (Windows)
1. Install Ollama and make sure the Ollama service is running.
2. Pull your local model, for example:
   `ollama pull qwen2.5-coder:7b`
3. Extract this ZIP to a permanent folder such as `C:\JARVIS`.
4. Copy `.env.production.example` to `backend\.env` for production or `.env.example` for development.
5. Set your `SECRET_KEY`, `AGENT_PAIRING_TOKEN`, and `VOICE_API_TOKEN` to long random values.
6. Keep `AI_PROVIDER=ollama`, `OLLAMA_ENABLED=true`, and set `OLLAMA_MODEL` to the model you installed.
7. Start JARVIS with `run_production.ps1` or the development uvicorn command.
8. Run `healthcheck.ps1`.
9. Start `laptop-agent\agent.py` with the same `AGENT_PAIRING_TOKEN`.

## Test the local AI connection
From `backend`:
```powershell
.\.venv\Scripts\Activate.ps1
python test_ai_providers.py
```
The test should report `SUCCESS: ollama / <your model>`.

## Important Ollama behavior
- Ollama runs on the local machine at `OLLAMA_BASE_URL` (default `http://127.0.0.1:11434`).
- JARVIS V9 does not perform built-in web grounding through the AI provider. Research reports generated by the Research Agent are explicitly offline hypotheses unless a future dedicated web-research tool is added.
- Your voice/STT settings are independent of the AI model. For fully offline voice, use the Vosk path described below.

## iPhone
Use `http://YOUR-PC-IP:8000/dashboard/remote.html` from Safari on the same trusted LAN. Add it to the Home Screen if desired. Do not port-forward the JARVIS server directly to the public Internet. For Internet access, use a VPN or authenticated HTTPS reverse proxy.

## Desktop safety
The laptop agent never accepts arbitrary shell commands. Desktop actions are allowlisted. URL opening and screen capture require explicit approval. Software-team commands remain approval-gated. The emergency-stop button cancels pending, approved and executing desktop actions that have not completed.

## Offline voice
Install `voice-agent\requirements-offline.txt`, download a Vosk model separately, set `JARVIS_VOSK_MODEL`, and set `JARVIS_OFFLINE_ONLY=true` to prevent cloud STT fallback.

## Production notes
- SQLite is suitable for a single-user/single-host deployment. For multi-user production, move to PostgreSQL and put JARVIS behind an HTTPS reverse proxy.
- Keep secrets and pairing/voice tokens out of source control.
- Do not run the JARVIS process as Administrator unless a deliberately designed feature requires it.
- Back up `backend\data\jarvis.db` and `workspace` regularly.
- This release is designed for controlled personal/LAN deployment; it is not an unattended public Internet service.

## Integrated V9.1 workflow

The integrated Ollama release now follows this lifecycle when you use **Dev Team -> Build a Product**:

1. Discovery: JARVIS analyzes the idea, requirements, unknowns, risks and definition of done.
2. Team assembly: JARVIS creates a dependency-aware plan and ensures every specialist role receives concrete work.
3. Automatic execution: ready independent tasks run in parallel waves; dependent tasks wait until their dependencies are complete.
4. Role execution: each agent works only within its assigned role and writes reviewable workspace artifacts.
5. QA review: completed tasks are automatically reviewed by the QA role.
6. Controlled actions: installs, tests/commands and other controlled operations still create approval requests instead of silently executing them.
7. Realtime dashboard: the dashboard refreshes every two seconds and can show browser notifications for new activity.
8. iPhone sync: remote voice conversations are written to dashboard chat history/activity when a dashboard user can be resolved. Explicit voice memory requests are stored in both the user memory profile and shared voice profile.

### Voice account mapping

For a single-user local installation, leave `VOICE_USER_EMAIL` blank and the voice bridge will attach history to the only dashboard account. If more than one account exists, set `VOICE_USER_EMAIL` in `backend/.env` to the intended dashboard account email.

### Important Ollama limitation

This V9 release is Ollama-only and has no built-in web search/grounding provider. The discovery phase therefore gathers information from the supplied project description, workspace context and the local model's knowledge. JARVIS must not claim that current web research was performed unless a real research/web tool is added later.


## V10 security and reliability notes

- Ollama remains the only AI provider. Set `OLLAMA_NUM_CTX=8192` and `AI_REQUEST_TIMEOUT_SECONDS=300` in `backend/.env` as needed for your hardware.
- Generate fresh values for `SECRET_KEY`, `AGENT_PAIRING_TOKEN`, and `VOICE_API_TOKEN`. Never share a populated `.env` or database-containing ZIP.
- Registration is open only until the first dashboard account is created. Login is throttled after repeated failed attempts (per server process).
- Approved commands are parsed with `shell=False`; shell chaining, inline Python/Node code, package installation commands, risky Git subcommands, absolute paths and parent-directory paths are rejected.
- Test commands still require explicit approval. Their exit code and captured output are saved against the task; failed verification queues a bounded repair task (up to three attempts).
- Each agent task attempts a pre-run and post-run Git checkpoint in the generated project workspace. The status is recorded in the task result; Git checkpoint failures are reported rather than falsely claiming a commit.
- A rejected review blocks the task and queues concrete repair work from its findings. Research prompts explicitly forbid fabricated interviews, statistics, quotes and sources.
- The dashboard uses `/api/live` and `/api/events` for near-real-time status; polling is the fallback where server-sent events are unavailable.

### Upgrade safely

1. Stop the current JARVIS backend.
2. Back up your existing `backend/.env` and `data/jarvis.db` somewhere private.
3. Extract this release into a new folder. Do not copy your old `.env` into a public/shared archive.
4. Create `backend/.env` from `backend/.env.example`, generate new random secrets locally, and preserve your existing database only if you intend to keep the same local account/history.
5. Install dependencies from `backend/requirements.txt`. For tests, install `backend/requirements-dev.txt` and run `python -m unittest discover -s tests -v` from the backend folder.
6. Start Ollama with the configured model, then start the backend using the included Windows script.

This release was syntax-checked and its command-policy regression tests were run in the build environment. Windows desktop-control and live Ollama end-to-end tests must still be performed on your own Windows machine.


## V10.1 team reliability update

- Agent-generated file batches are validated before writes; duplicate paths, `.git` paths, `.env` files, oversized files and oversized batches are rejected.
- Command classification uses the command text rather than trusting an AI-supplied `kind` label. A script cannot be treated as a passing test merely because the model labels it `test`.
- Approval execution claims an approval before running it, prevents repeat execution, and records success/failure.
- Completing or failing an approved test resumes the project's dependency-aware workflow so dependent work or bounded repair work can continue.
- Regression tests cover command classification and existing command-policy behavior.
